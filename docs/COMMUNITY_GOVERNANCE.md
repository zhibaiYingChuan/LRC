# Loong Recall 社区治理白皮书

## 一、治理哲学

Loong Recall 的治理遵循"中宫调和"原则——不偏向任何一方，在实用主义与哲学追求之间寻找平衡。

我们相信，优秀的软件不是由单一的权威塑造出来的，而是由社区在清晰的规则和共同的价值观引导下，持续演化而成的。本白皮书将 DaoEvolutionProtocol 的代码逻辑转化为现实世界中可执行的社区治理规则。

## 二、治理层级

### 2.1 核心维护者（Core Maintainers）

核心维护者是项目的最终守护者，承担着维护项目哲学一致性的责任。

- **权限**：拥有仓库写权限
- **职责**：
  - 负责 L2 核心哲学层的代码审查
  - 对道枢映射的变更拥有否决权
  - 维护 DaoEvolutionProtocol 的演化代际记录
  - 仲裁哲学层面的分歧
- **任期**：核心维护者不设固定任期，但若连续 6 个月无活跃贡献，将自动转为荣誉维护者（Emeritus Maintainer）
- **增选**：新核心维护者由现有核心维护者一致同意后增选

### 2.2 贡献者（Contributors）

贡献者是项目的中坚力量，通过代码、文档或测试推动项目发展。

- **权限**：通过 PR 贡献代码
- **审查规则**：
  - L1 应用层的 PR 只需 1 位核心维护者审查
  - L2 核心哲学层的 PR 需要 2 位核心维护者审查
  - L3 外部接口层的 PR 需要 1 位核心维护者 + 1 位贡献者审查
- **成为贡献者**：任意社区成员在合并 3 个有效 PR 后，自动获得贡献者身份

### 2.3 社区成员（Community Members）

社区成员是项目生态的基础，每一个人都是道的一部分。

- **权限**：参与讨论、提交 Issue、对提案投票
- **参与方式**：
  - 在 Discussions 中参与技术讨论
  - 提交 Bug Report 或 Feature Request
  - 对道枢演化提案发表意见
  - 编写文档和教程

## 三、DaoEvolutionProtocol 的现实落地

### 3.1 提案流程

DaoEvolutionProtocol 定义了代码中道枢映射的演化规则，在社区治理中，我们将其映射为以下流程：

1. 任何社区成员可在 GitHub Issues 中提交"道枢演化提案"（使用 `dao-proposal` 标签）
2. 提案必须包含：
   - **哲学基础**：为什么这个变化符合道？（引用道枢映射表中的相关条目）
   - **实际收益**：用户能得到什么？（具体的功能改进或性能提升）
   - **影响范围**：涉及 L1/L2/L3 哪个层面？
3. 核心维护者在 14 天内进行初步审查，标记为：
   - **接受审查**：提案合理，进入投票阶段
   - **需要修改**：提案需要补充信息或调整范围
   - **驳回**：提案不符合项目哲学

### 3.2 投票机制

投票是 DaoEvolutionProtocol 中道枢涌现的社区表达方式。

- **投票人资格**：
  - 核心维护者每人 1 票
  - 贡献者（过去 6 个月有合并 PR）每人 1 票
- **表决规则**：
  - 提案需获得 2/3 多数通过
  - 投票期为 14 天
  - 投票在 GitHub Issue 中以 👍（赞成）/ 👎（反对）反应进行
- **法定人数**：至少 3 位有投票权成员参与表决

### 3.3 演化接受

通过的提案按以下流程落地：

1. 由核心维护者（或指定的贡献者）实现
2. 在代码中以 `@涌现` 标记记录新的道枢映射
3. 更新 `DaoEvolutionProtocol` 中的演化代际计数器
4. 在本白皮书第七章"演化日志"中记录

### 3.4 紧急演化

在以下情况下，核心维护者可绕过常规流程快速决策：

- 安全漏洞修复
- 重大功能回退
- 许可证合规问题

紧急演化需事后在 7 天内补交提案说明，并接受社区复审。

## 四、红线与底线

### 4.1 不可变更的核心（L2 红线）

以下部分构成了 Loong Recall 的哲学基础，不可通过常规提案变更：

- 洛书编码器的 9 维约束
- 镜像梯形递归算子
- 道同构度定义
- 审计链防篡改机制

修改这些核心需要全体核心维护者一致同意，并附带完整的哲学论证。

### 4.2 可演化的部分

以下部分欢迎社区提案：

- 编码器优化策略
- 合成算法变体
- 用户界面设计
- 新的道枢映射关系
- API 接口设计
- 文档和教程

## 五、冲突解决

### 5.1 技术分歧

技术层面的分歧通过数据和实验解决：

- 通过 Benchmark 数据决定性能相关的争议
- 建立 A/B 测试框架用于用户体验相关的决策
- 鼓励提交可复现的最小示例来支持论点

### 5.2 哲学分歧

哲学层面的分歧按照以下层级解决：

1. 核心维护者组织讨论，充分听取各方意见
2. 引用 DaoEvolutionProtocol 中的道枢映射作为参考框架
3. 若无法达成共识，由项目创始人最终裁决（如同中宫统摄八方）
4. 裁决结果记录在演化日志中，作为未来决策的参考

### 5.3 行为准则违规

所有参与者必须遵守行为准则（CODE_OF_CONDUCT.md）。违规处理：

1. 首次违规：警告
2. 二次违规：暂停参与权限 30 天
3. 三次违规：永久移除

## 六、许可证治理

Loong Recall 采用分层许可证策略，体现不同层级的哲学意义：

- **核心引擎（L2）**：DaoTi Research License v1.0 —— 保护核心哲学代码的完整性
- **应用层（L1）**：Apache 2.0 —— 鼓励广泛使用和商业应用
- **外部接口层（L3）**：MIT —— 最大化兼容性

贡献者在提交第一个 PR 时需签署 CLA（Contributor License Agreement），确认其贡献可在上述许可证下发布。
