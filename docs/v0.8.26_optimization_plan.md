## 三、分阶段修复路线图

### 阶段一：P0 必修复（发布前必须完成）

| ID | 标题 | 文件 | 修改内容 | 预期工时 | 风险等级 |
|----|------|------|---------|---------|---------|
| REL-01 | index.html status-version 盲点 | `static/index.html:2131` | 将 `id="status-version"` 内联版本号改为动态获取，并纳入 preflight 检查 | 0.5h | 低 |
| REL-02 | security.yml cargo-license SHA 锁定 | `.github/workflows/security.yml:86-88` | 将 `cargo-license` 安装步骤固定到指定版本（如 `cargo-license@0.6.1`） | 0.3h | 低 |
| CI-01 | Rust 编译器版本固定 | `.github/workflows/ci.yml:41,68,107,147` | 将 `dtolnay/rust-toolchain` 的 `stable` 改为 `1.80.0`，同步 release.yml | 0.3h | 低 |

#### REL-01 详细方案

**问题**：`index.html` 第 2131 行 `<strong id="status-version">v0.8.25</strong>` 包含硬编码版本号。release.yml 的 preflight 检查已覆盖 `meta name="version"`（第 9 行），但未检查 `status-version` 内联文本。发布时此盲点会导致版本号显示滞后。

**修复方案**：
1. `static/index.html` — 将 `id="status-version"` 的内容改为动态获取（从 `meta name="version"` 读取或从 API 响应获取），移除硬编码值
2. `.github/workflows/release.yml` — preflight 版本一致性检查中增加对 `static/index.html` 中 `status-version` 的检查

**修改详情**：

```html
<!-- 修改前 (index.html:2131) -->
<span>版本 <strong id="status-version">v0.8.25</strong></span>

<!-- 修改后 -->
<span>版本 <strong id="status-version">v0.8.26</strong></span>
```

并在 `app.js` 中增加逻辑：页面加载后从 `meta[name="version"]` 读取版本号，若不一致则更新。

**验证**：运行 `python3 -c "import re; html=open('static/index.html').read(); assert re.search(r'id=\"status-version\">v0\.8\.26<', html), 'status-version 未同步'"`

#### REL-02 详细方案

**问题**：`security.yml` 第 86-88 行 `cargo install cargo-license` 未锁定版本，每次 CI 运行都从 crates.io 安装最新版，既增加 CI 耗时（约 60-120s），又引入不可重现风险。

**修改详情**：

```yaml
# 修改前
- name: Install cargo-license
  run: |
    timeout 120 cargo install cargo-license --locked || timeout 120 cargo install cargo-license

# 修改后
- name: Install cargo-license
  run: |
    # 锁定到 0.6.1 版本，确保 CI 可重现性
    timeout 120 cargo install cargo-license --version 0.6.1 --locked || \
      timeout 120 cargo install cargo-license --version 0.6.1
```

**验证**：CI 运行 license-check job，安装时间应显著缩短，且版本固定在 0.6.1。

#### CI-01 详细方案

**问题**：所有 CI workflow 使用 `dtolnay/rust-toolchain@... # stable`，未固定到具体版本。`Cargo.toml` 已声明 `rust-version = "1.80"`，但 CI 可能使用不同版本，导致构建结果不可重现。

**修改详情**：

```yaml
# 修改前（所有出现 stable 的地方）
- uses: dtolnay/rust-toolchain@4cda84d5c5c54efe2404f9d843567869ab1699d4 # stable

# 修改后
- uses: dtolnay/rust-toolchain@4cda84d5c5c54efe2404f9d843567869ab1699d4
  with:
    toolchain: 1.80.0
```

**涉及文件**：`ci.yml`（4 处）、`security.yml`（1 处）、`release.yml`（3 处）

**验证**：CI 运行后检查日志中 `rustc --version` 输出是否为 `1.80.0`。

#### ARC-01 详细方案（app.js 模块拆分）

**问题**：`static/app.js` 文件 370KB、约 12000+ 行，是典型的前端单体文件。主要问题：
- 可维护性差：修改一个功能需要搜索整个文件
- 加载性能：单文件加载，无并行下载
- 团队协作：多人同时编辑同一文件容易冲突

**拆分策略**（按功能域，不重构逻辑）：

```
static/
├── app.js                      # 入口文件（路由分发 + 公共工具函数 + 状态管理）
├── app-core.js                 # 核心模块：API 客户端、Toast、模态框、加载状态
├── app-dashboard.js            # 仪表盘：道同构度、统计卡片、快速操作、向导
├── app-search.js               # 记忆搜索：搜索输入、筛选面板、卡片流、详情面板
├── app-settings.js             # 设置：LLM 配置、模型管理、备份恢复、关于
├── app-trust.js                # 信任中心：隐私检查、数据位置、网络审计、备份
└── app-benchmarks.js           # 基准报告：标签切换、雷达图、对比表格
```

**实施步骤**：
1. 创建模块文件，从 `app.js` 中按功能域提取函数
2. 保留 `app.js` 作为入口，`import` 各模块（或使用 `<script>` 标签按顺序加载）
3. 验证每个模块的导出/导入正确性
4. 更新 `index.html` 的 `<script>` 标签顺序

**风险控制**：
- 拆分后保持函数签名不变，不修改任何业务逻辑
- 每次提取一个模块，完成后立即运行仪表盘验证
- 回退方案：如果拆分引入回归，可回滚到单一文件，以 `<script>` 标签顺序加载替代

#### ARC-02 详细方案（agent_detector.rs 模块拆分）

**问题**：`desktop/src-tauri/src/agent_detector.rs` 文件 150KB，是桌面端第二大源文件。包含：
- 工具检测逻辑（扫描 36+ IDE/Agent）
- MCP 配置生成
- 项目发现
- 规则文件写入
- 配置向导状态管理

**拆分策略**：

```
desktop/src-tauri/src/
├── agent_detector.rs           # 入口：重新导出子模块 + 公共类型
├── detector/
│   ├── mod.rs                  # 模块声明 + 重新导出
│   ├── scanner.rs              # 工具扫描检测（从原文件提取扫描逻辑）
│   ├── config.rs               # MCP 配置生成（从原文件提取配置逻辑）
│   ├── writer.rs               # 规则文件写入（从原文件提取写入逻辑）
│   └── types.rs                # 公共类型定义（从原文件提取类型定义）
```

**风险控制**：
- 与原文件 ARC-01 类似，保持函数签名不变
- 先在 `lib.rs` 中声明 `mod detector;`，再逐步迁移

#### REG-01 详细方案（超时对齐）

**问题**：`onAgentSelected` 前端超时设为 15 秒，后端对应操作的超时设为 30 秒。前端超时先触发，用户看到超时错误，但后端操作仍在继续，造成状态不一致。

**修复方案**：将前端超时调整为 25 秒（后端 30 秒 - 5 秒缓冲），确保后端超时先触发，前端能捕获到后端返回的错误信息。

**修改位置**：
- 前端 `app.js` 中找到 `onAgentSelected` 的超时设置，将 `15000` 改为 `25000`
- 或：后端 `agent_detector.rs` 中找到对应操作的超时，将 `30000` 改为 `15000`（更优，因为前端更适合显示快速反馈）

#### CI-02 详细方案（前端 UI 自动化测试）

**问题**：现有 CI 覆盖了 Rust 后端（fmt/clippy/test/E2E smoke），但前端仪表盘（`static/` 目录）无任何自动化测试。仪表盘的主要风险：
- HTML 结构变更导致 JS 选择器失效
- API 端点变更导致前端数据渲染异常
- 交互逻辑回归（如模态框无法打开）

**实施计划**：

```javascript
// tests/frontend/dashboard-smoke.spec.js
// 基于 Playwright 的仪表盘冒烟测试
// 覆盖路径：
// 1. 页面加载 → 侧边栏可见
// 2. 标签页切换（仪表盘 → 搜索 → 设置）
// 3. 健康端点 mock → 道同构度渲染
// 4. 状态栏版本号显示
```

**实施步骤**：
1. 在 `tmp/` 或 `tests/frontend/` 创建 Playwright 测试脚本
2. 在 `ci.yml` 中新增 `frontend-test` job（仅在 `static/` 目录变更时触发）
3. 使用 `actions/upload-artifact` 上传测试报告

**风险**：需要安装 Playwright 和浏览器，增加 CI 约 30-60s。

#### UX-01 详细方案

**问题**：`setButtonState` 按钮文本恢复延迟为 1.5s，而 `testModel` 的边框高亮恢复延迟为 5s。用户在同一页面操作时，会感知到两种不同的恢复节奏，造成视觉不一致。

**修复方案**：统一为 3s（折中值，既不过快导致用户看不清反馈，也不过慢影响连续操作）。

**修改位置**：
- 在 `app.js` 中搜索 `setButtonState` 和 `testModel` 的恢复延迟设置
- 将两者统一为 `3000` ms

#### UX-02 详细方案

**问题**：`_lockBusyCooldownTimer` 在冷却期间显示消息，但用户切换 tab 后，冷却期信息丢失。返回时用户不知道操作是否还在进行。

**修复方案**：
- 使用 `sessionStorage` 存储冷却期状态（`busy_lock_state` + `expiry_timestamp`）
- 页面加载时检查 `sessionStorage`，若冷却期未过期则恢复显示

**修改位置**：`app.js` 中 `_lockBusyCooldownTimer` 相关代码

#### UX-03 详细方案

**问题**：桌面端 `start_sidecar` 操作无进度事件推送，前端无法感知启动进度。用户点击"启动服务"后，只能等待"已停止"→"运行中"状态跳变。

**修复方案**：
1. 后端 `sidecar_manager.rs`：在 `start_sidecar` 过程中发送进度事件（如 `started→loading_model→indexing→ready`）
2. 前端 `app.js`：监听进度事件，在状态栏显示进度文本（如"正在加载模型..."、"正在索引代码..."）

### B. RICE 评分说明

- **Reach**: 受影响的用户/场景比例（高/中/低）
- **Impact**: 修复后的影响程度（极严重/严重/中/低）
- **Confidence**: 修复方案的确信度（高/中/低）
- **Effort**: 预估工时（小/中/大）
- **RICE 分**: Reach × Impact × Confidence / Effort（极高/高/中/低）
