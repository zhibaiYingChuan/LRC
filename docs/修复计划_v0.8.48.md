### FIX-002 修复 `synthesis_pending` 竞态条件
| 项 | 值 |
|----|----|
| 优先级 | **P0** |
| 难度 | 中 |
| 可并行 | 可 |

- **问题描述**：`memory_store.rs` 中 `synthesis_pending` 使用普通 `bool`，多后台任务并发读写时可能**重复执行或遗漏合成**（竞态条件）。
- **具体位置**：`src/memory_store.rs:236-239`（字段声明），以及所有读写该字段的位置（写入记忆后置 `true`、后台健康检查读取置 `false`）。
- **修复方案**：改用 `AtomicBool` + `compare_exchange` 实现原子性。

```rust
// 原：
pub synthesis_pending: bool,
// 改为：
pub synthesis_pending: std::sync::atomic::AtomicBool,
```

置位（写入记忆后触发合成）——使用 `compare_exchange` 保证**只有一个后台任务**能抢占执行：

```rust
// 抢占合成执行权：仅第一个成功切换 true→false 的任务执行合成
if self
    .synthesis_pending
    .compare_exchange(true, false, Ordering::AcqRel, Ordering::Acquire)
    .is_ok()
{
    // 执行 luoshu_synthesize()
}
```

同时需审查 `gc_pending`（`:236`）是否有同类问题，若存在一并修复。
- **验证方法**：编写并发测试，模拟多任务同时触发合成，断言合成只执行一次；`cargo test`。
- **预估工作量**：2 小时。

### FIX-006 修复 `AppState` 全局锁竞争
| 项 | 值 |
|----|----|
| 优先级 | **P0** |
| 难度 | 中 |
| 可并行 | 可 |

- **问题描述**：`server.rs:233-247` 的 `AppState` 使用 `Mutex` 而非 `RwLock`，后台任务长时间持锁导致前端请求 503。
- **具体位置**：`src/server.rs:233-247`（`AppState` 结构体）。
- **修复方案**：将 `manager` 与 `memory_store` 从 `Arc<Mutex<...>>` 改为 `Arc<RwLock<...>>`，读请求用 `read()`，写请求用 `write()`。

```rust
pub struct AppState {
    pub manager: Arc<RwLock<Box<dyn IndexedCodebase>>>,
    pub memory_store: Arc<RwLock<MemoryStore<JsonPersistence>>>,
    // ... 其余不变
}
```

> 注意：`RwLock` 的写锁仍会阻塞读，需同时配合 `FIX-007` 避免后台任务长时间持写锁。
- **验证方法**：并发压测（多读 + 后台写），观察前端请求不再 503；`/health` 在后台任务执行时仍快速响应。
- **预估工作量**：3 小时。

### FIX-007 修复 `spawn_blocking` + `blocking_lock` 阻塞线程池
| 项 | 值 |
|----|----|
| 优先级 | **P0**（与 FIX-006 配合） |
| 难度 | 中 |
| 可并行 | 可 |

- **问题描述**：`consolidation.rs:369-382` 使用 `spawn_blocking` + `blocking_lock()`，`blocking_lock` 会阻塞 tokio 阻塞线程池中的线程，若锁被持有则整个线程池线程被占用。
- **具体位置**：`src/consolidation.rs:369-382`。
- **修复方案**：避免在 `spawn_blocking` 闭包内持有 `blocking_lock` 长时间运行。改为：
  1. 先将锁内需要的数据提取出来（`&` 读），再在 `spawn_blocking` 中执行纯计算；
  2. 或使用 `tokio::sync::Mutex` + `await`（非阻塞线程池）。
- **验证方法**：并发触发合成任务，观察线程池不再被占满；`/health` 持续响应。
- **预估工作量**：3 小时。
