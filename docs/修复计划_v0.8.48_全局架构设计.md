# code-memory v0.8.48 全局架构级修复计划

> **核心原则**：不打补丁，全局重构架构。  
> **审计依据**：综合评分 6.6/10 的六维度审计报告  
> **修复周期**：v0.8.48（结构优化）→ v0.8.49（并发安全）→ v0.9.0（大版本重构）

## 第一部分：全局架构设计原则（8 条）

### 1. **职责单一原则（Single Responsibility）**
- 每个模块只负责一件事
- 当前问题：`server.rs` 混合 7 种职责（MCP 类型、路由、工具检测、嵌入模型、健康检查、配置、注册）
- 目标：拆分为 8 个独立模块，每个模块 ≤ 1000 行

### 2. **模块化优先**
- 后端：按职责拆分模块（mcp_types, routes, tools, embed, health, config）
- 前端：从单文件 9749 行拆分为 10+ 模块（main, api, dashboard, search, trust, captain, mcp-config, benchmark, errors, utils）

### 3. **并发安全隔离**
- 共享状态最小化
- 使用 `AtomicBool`、`RwLock`、`tokio::sync::Mutex` 替代普通 `Mutex`
- 后台任务不得长时间持锁

### 4. **异步第一**
- 避免 `spawn_blocking` + `blocking_lock` 组合
- 用 `tokio::sync::Mutex` + `await` 替代阻塞锁

### 5. **兜底反馈机制**
- 五层交互韧性（L1-L5）：每一层都有超时、错误、降级方案
- 用户感知：加载态、进度条、错误提示、自动重试

### 6. **测试驱动**
- P0 修复：先写测试，再修复代码
- 并发测试、集成测试、端到端测试

### 7. **可观测性**
- 关键路径的日志、指标、追踪
- 错误日志包含：类型、位置、变量值、堆栈

### 8. **文档即代码**
- 架构文档与代码同步维护
- 修复完成后立即更新 `ARCHITECTURE.md`

4. `handlers/*`：每个业务模块单独文件

### 并发安全隔离设计

#### 问题 1：`synthesis_pending` 普通 bool 竞态 → **P0 在 v0.8.48**

```rust
// 原始代码（不安全）
pub struct MemoryStore<P: Persistence> {
    pub synthesis_pending: bool,  // ❌ 竞态条件
    pub gc_pending: bool,         // ❌ 竞态条件
    // ...
}

// 修复后（原子操作）
pub struct MemoryStore<P: Persistence> {
    pub synthesis_pending: AtomicBool,  // ✅ 原子操作
    pub gc_pending: AtomicBool,         // ✅ 原子操作
    // ...
}

// 使用模式
// 1. 抢占执行权（只有一个线程能获取）
if self.synthesis_pending
    .compare_exchange(true, false, Ordering::AcqRel, Ordering::Acquire)
    .is_ok()
{
    // 执行合成
    self.luoshu_synthesize().await?;
}

// 2. 标记需要合成
self.synthesis_pending.store(true, Ordering::Release);

// 3. 查询状态
if self.synthesis_pending.load(Ordering::Acquire) {
    // 处理合成中状态
}
```

#### 问题 2：`spawn_blocking` + `blocking_lock` 阻塞线程池 → **P0 在 v0.8.48**

```rust
// 原始代码（问题）
tokio::task::spawn_blocking(move || {
    let mut store = store.blocking_lock();  // ❌ 阻塞线程池中的线程
    // 长耗时操作...
    store.luoshu_synthesize();
})

// 修复方案 1：用 tokio::sync::Mutex
let store = Arc::new(tokio::sync::Mutex::new(...));
tokio::spawn(async move {
    let mut store = store.lock().await;  // ✅ 非阻塞等待
    // 操作...
    store.luoshu_synthesize().await;
})

// 修复方案 2：先提取数据，再在 spawn_blocking 中计算
let data = {
    let store = store.lock().unwrap();
    store.get_data_for_synthesis()  // 快速读取，立即释放锁
};

tokio::task::spawn_blocking(move || {
    // 不持锁的纯计算
    let result = compute_synthesis(data);
    // 最后短时间持锁写回
    let mut store = store.blocking_lock();
    store.write_synthesis_result(result);
})
```

#### 问题 3：`AppState` 全局锁竞争 → **P1 在 v0.8.49**

```rust
// 原始代码
pub struct AppState {
    pub manager: Arc<Mutex<Box<dyn IndexedCodebase>>>,
    pub memory_store: Arc<Mutex<MemoryStore<JsonPersistence>>>,
}

// 修复后（读写分离）
pub struct AppState {
    pub manager: Arc<RwLock<Box<dyn IndexedCodebase>>>,
    pub memory_store: Arc<RwLock<MemoryStore<JsonPersistence>>>,
}

// 使用模式
// 读操作
let store = state.memory_store.read().await;
let memories = store.recall(...)?;

// 写操作
let mut store = state.memory_store.write().await;
store.remember(...)?;
```
