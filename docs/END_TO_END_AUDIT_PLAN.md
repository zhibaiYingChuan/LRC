# LRC 端到端审计计划 v1.0

> **创建时间**: 2026-07-28
> **创建原因**: v0.6.0 多个功能失效问题未被静态审计发现,需要新的审计维度
> **适用范围**: 桌面端 + IDE 插件 + sidecar

## 1. 问题根源分析

### 1.1 为什么静态审计发现不了这些问题?

| 问题 | 静态审计视角 | 实际失效原因 |
|------|-------------|-------------|
| start_sidecar 不传 src_dir | 代码编译通过,无语法错误 | 前端 invoke 调用缺少参数,功能链路断裂 |
| wizard.json project_dir 未使用 | 配置层正确保存了字段 | 执行层不读取该字段,配置-执行断链 |
| API 方法不匹配(GET vs POST) | 前端代码逻辑正确 | 前端 POST 调用 GET 端点,运行时 405 |
| 导入格式不兼容 | 导入逻辑正确 | 未处理老版本数组格式,运行时解析失败 |

### 1.2 静态审计的局限性

```
静态审计能看到:          静态审计看不到:
✓ 代码语法正确           ✗ 前端→后端参数是否传递
✓ 类型检查通过           ✗ API 方法是否匹配
✓ 无安全漏洞             ✗ 配置字段是否被使用
✓ 代码规范符合           ✗ 数据流是否完整
✓ 编译通过               ✗ 运行时行为是否正确
```

## 2. 新审计维度:功能链路审计

### 2.1 五层审计模型

```
Layer 1: 静态代码审计(已有)
  ├─ 代码质量
  ├─ 安全扫描
  ├─ 编译检查
  └─ 规范符合

Layer 2: 配置-执行链路审计(新增)        ← 发现 wizard.project_dir 未使用
  ├─ 配置字段使用率检查
  ├─ 参数传递完整性检查
  ├─ 默认值回退合理性检查
  └─ 环境变量传递检查

Layer 3: API 契约审计(新增)             ← 发现 GET/POST 不匹配
  ├─ HTTP 方法一致性
  ├─ 请求体格式匹配
  ├─ 响应体解析正确性
  └─ 错误码处理完整性

Layer 4: 数据流审计(新增)               ← 发现记忆导入格式不兼容
  ├─ 数据格式兼容性
  ├─ 数据迁移路径
  ├─ 数据持久化验证
  └─ 数据恢复验证

Layer 5: 端到端场景审计(新增)           ← 发现指纹目录泛滥
  ├─ 用户场景模拟
  ├─ 跨层调用验证
  ├─ 异常恢复测试
  └─ 用户体验验证
```

### 2.2 审计检查清单

#### Layer 2: 配置-执行链路审计

| 检查项 | 检查方法 | 工具 |
|--------|---------|------|
| Tauri 命令参数传递 | 对比前端 invoke 调用与 Rust 函数签名 | Grep + 人工 |
| wizard.json 字段使用率 | 搜索每个字段在 Rust 代码中的引用 | Grep |
| 默认值回退合理性 | 检查 Option<T> 的 unwrap_or_else 逻辑 | 代码审查 |
| 环境变量传递 | 检查 cmd.env() 与 sidecar 读取的变量 | Grep |

#### Layer 3: API 契约审计

| 检查项 | 检查方法 | 工具 |
|--------|---------|------|
| HTTP 方法一致性 | 对比前端 fetch method 与 Rust route 定义 | Grep |
| 请求体格式 | 对比前端 body JSON 与 Rust Json<T> 结构 | 代码审查 |
| 响应体解析 | 对比 Rust 响应 JSON 与前端解析逻辑 | 代码审查 |
| API 路径一致性 | 对比前端 API_BASE + path 与 Rust route | Grep |

#### Layer 4: 数据流审计

| 检查项 | 检查方法 | 工具 |
|--------|---------|------|
| 数据格式兼容性 | 检查导入逻辑是否处理所有历史格式 | 代码审查 |
| 数据迁移路径 | 检查老版本数据到新版本的迁移逻辑 | 场景模拟 |
| 数据持久化验证 | 验证写入的数据能正确读回 | 集成测试 |
| 数据恢复验证 | 验证导出的数据能正确导入 | E2E 测试 |

#### Layer 5: 端到端场景审计

| 场景 | 验证步骤 | 预期结果 |
|------|---------|---------|
| 首次启动 | 安装 → 启动 → 查看仪表盘 | 服务正常启动,无空目录 |
| 记忆写入 | UI 触发 remember → 检查文件系统 | memories.json 有新记录 |
| 记忆检索 | UI 触发 recall → 检查返回结果 | 返回相关记忆 |
| 记忆导出 | UI 触发导出 → 检查下载文件 | JSON 文件完整 |
| 记忆导入 | UI 触发导入 → 检查记忆库 | 记忆正确写入 |
| 项目切换 | UI 切换项目 → 检查数据目录 | 数据目录正确切换 |
| 老版本迁移 | 复制老版本数据 → 启动 → 检查 | 数据正确加载 |

## 3. 审计执行流程

### 3.1 每次发布前必须执行

```
Step 1: Layer 1 静态审计(自动)
  └─ cargo clippy + cargo test

Step 2: Layer 2 配置-执行链路审计(半自动)
  ├─ 运行 scripts/audit_config_chain.py(待创建)
  └─ 人工复核异常项

Step 3: Layer 3 API 契约审计(自动)
  └─ 运行 scripts/audit_api_contract.py(待创建)

Step 4: Layer 4 数据流审计(半自动)
  ├─ 运行导入/导出测试
  └─ 验证数据完整性

Step 5: Layer 5 端到端场景审计(手动)
  └─ 按 checklist 逐项验证
```

## 4. 推荐智能体组合

### 4.1 审计阶段智能体选择

| 审计维度 | 推荐智能体 | 理由 |
|---------|-----------|------|
| Layer 1 静态审计 | code-review 技能 | 代码质量检查 |
| Layer 2 配置链路 | project-onboarding-auditor | 全景分析配置使用 |
| Layer 3 API 契约 | general_purpose_task | 跨层对比 API 定义 |
| Layer 4 数据流 | auto-debugger | 数据流追踪 |
| Layer 5 端到端 | browser_use / 网页应用测试 | 浏览器自动化测试 |

### 4.2 分析方法论

使用 **Shannon 六钥匙** 分析审计问题:

1. **简化**: 核心问题是"静态审计无法发现动态行为问题"
2. **重述**: 从用户视角看,功能能用才是标准
3. **泛化**: 这是"集成测试缺失"的经典问题
4. **分解**: 按功能链路逐层审计
5. **繁衍**: 从"用户不会遇到问题"反推审计需求
6. **类比**: 汽车制造需要路试,软件需要 E2E 测试
