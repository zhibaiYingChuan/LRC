## 三、修复计划

### 修复 F1：showConfirm 默认超时机制（D-01）

| 维度 | 内容 |
|------|------|
| **问题描述** | `showConfirm` 默认 `timeoutMs=0`，用户长时间不操作时 Promise 永久 pending，调用方被永久阻塞 |
| **严重度** | **P2**（RPN 150，HCSE 高 RPN 项） |
| **代码位置** | `static/app.js:L4194` — `function showConfirm(message, title = '确认操作', timeoutMs = 0)` |
| **修复方案** | 将默认 `timeoutMs` 从 `0` 改为 `60000`（60s），超时自动 reject 并 `showToast("操作超时已取消", "warning")` |
| **预期影响** | 消除确认对话框永久 pending 风险，提升 L2 弹窗韧性 |
| **风险等级** | **低** — 纯参数默认值变更，不影响已有逻辑；调用方已处理 reject 场景 |
| **副作用分析** | 无。现有代码中 `timeoutMs > 0` 分支已有超时处理逻辑，仅需修改默认值 |
| **预估修改量** | **1 行** — 修改函数签名默认参数 |
| **同类修复** | 无同类问题，独立修复 |

### 修复 F5：lock_busy 重试循环无上限保护

| 维度 | 内容 |
|------|------|
| **问题描述** | `loadDashboard` 中 lock_busy 重试 3 次耗尽后，如果用户手动刷新再次遇到 503，会再次进入重试循环，形成无限循环模式 |
| **严重度** | **P2**（RPN 120，重试缺乏全局上限保护） |
| **代码位置** | `static/app.js:L926-L955` — lock_busy 处理分支 |
| **修复方案** | 在 `_dashboardRetryCount >= _DASHBOARD_MAX_RETRIES` 后，添加 30 秒冷却期（`_lockBusyCooldown` 标志），冷却期内直接显示"后台合成中，建议 30 秒后重试"文案，不触发自动重试 |
| **预期影响** | 防止手动刷新后再次进入重试循环，提升重试机制的健壮性 |
| **风险等级** | **中** — 涉及重试逻辑变更，需要确保冷却期结束后恢复正常重试 |
| **副作用分析** | 可能延长用户在极端情况下的等待时间（但优于无限循环）。冷却期结束后需确保 `_lockBusyCooldown` 正确清除 |
| **预估修改量** | **8-10 行** — 添加冷却期标志 + 检查逻辑 |
| **同类修复** | 检查是否还有其他模块（如 trust center）存在类似的无上限重试模式 |

## 七、六钥匙（Shannon Six Keys）使用标注

以下为需要复杂判断的修复，建议使用六钥匙方法：

### 6K-1: 船长日志缓存策略（F6）

**问题复杂性**：需要在"降级时显示缓存"和"数据可能过时"之间权衡，涉及缓存写入时机、失效策略、用户提示。

**六钥匙评估**：
- **复杂度**：中（3 个状态：成功/降级/完全失败）
- **不确定性**：中（缓存读取时机、降级路径状态判断）
- **风险**：中（缓存数据误导用户）

**建议**：使用六钥匙进行详细设计，重点考虑缓存时效标记和用户提示文案。

### 6K-2: 信任中心缓存策略（F7）

**问题复杂性**：涉及 4 个独立函数之间的缓存共享，需考虑缓存一致性。

**六钥匙评估**：
- **复杂度**：中（4 个读写点 + 1 个失效点）
- **不确定性**：低（缓存模式清晰）
- **风险**：低（30s 缓存窗口，信任数据变化慢）

**建议**：使用六钥匙确认缓存 key 设计和失效策略。
